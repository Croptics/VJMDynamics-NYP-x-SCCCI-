MUSTERGO — PROJECT STRUCTURE NOTES
====================================
(What each file does, organized by folder)


ROOT LEVEL
----------
permissions.js
    The single source of truth for permissions. Both frontend and backend
    import this one file. Defines the 5 permissions (manageDelegates,
    manageTrips, manageExceptions, exportData, manageAccounts) — add one
    entry here and the checkbox/chip/enforcement appear everywhere
    automatically.

README.md / HIGH_LEVEL_DESIGN.md / PROJECT_IMPLEMENTATION_PHASE.md
    Docs — setup instructions, architecture/DB schema notes, and the team's
    sprint plan.

.gitignore
    Excludes .claude/, node_modules/, and other local-only files from git.

.claude/
    My (Claude Code) own tooling config — dev-server launch settings etc.
    Not part of the app itself; gitignored, never pushed to GitHub.

qr-test-codes/
    Two ready-made QR images for testing the /checkin screen's QR pill
    (qr-attendance-registered.png = a valid MusterGo delegate badge,
    qr-code-invalid.png = junk that should show "QR code invalid") plus
    qr-payloads.txt with the raw JSON each one encodes.


BACKEND/  (Express API, port 4000)
-----------------------------------
server.js
    The Express app itself. Defines every API route: login/session,
    dashboard reads, delegate CRUD, Excel export, account management.
    Read routes (trips/dashboard/missing/delegates) require any signed-in
    account via requireAuth(); mutating routes and export require a
    specific permission via requirePermission() (both from auth.js). Has a
    "TEAMMATE ZONE" comment near the bottom — the sanctioned spot for
    teammates to plug in their own route files (e.g. routes/insights.js
    is mounted here).
    The credential endpoints (POST /api/auth/login and /api/auth/reset-
    password) are wrapped in a tiny in-memory rateLimit() middleware —
    10 attempts per 10 minutes per IP, returns 429 + Retry-After when
    exceeded, and a successful login clears that IP's counter so normal use
    is unaffected. No dependency and no shared store (fine for this single-
    instance app; a multi-instance deploy would move it to Redis / express-
    rate-limit). Also warns at startup if FRONTEND_URL isn't set, because
    CORS then reflects ANY origin — fine for the local Vite proxy, must be
    set before a public deploy (mirrors auth.js's JWT_SECRET warning).

    POST /api/auth/logout — requireAuth()-gated; calls clearLastSeen() on the
    caller's own account so Staff Operations' "active now" list reflects an
    explicit logout right away. Frontend fires this best-effort (fire-and-
    forget, errors ignored) from App.jsx's handleLogout BEFORE clearToken()
    wipes the JWT it needs — the local logout (clearToken + redirect to
    /login) proceeds regardless of whether this call succeeds.

auth.js
    Session tokens + auth middleware, shared by server.js and any
    teammate route file that needs to require a signed-in caller (e.g.
    routes/insights.js, routes/desmond.js, routes/exceptions.js). Issues
    signed JWTs (makeToken) and exports accountFromReq / requireAuth /
    requirePermission. accountFromReq also accepts the token as a ?token=
    query param (not just the Authorization header) — needed for Jayden's
    SSE route, since EventSource can't set custom headers. Set JWT_SECRET in
    backend/.env before deploying anywhere public — without it a fixed
    dev-only fallback is used and a warning prints on startup.

data.js
    The database layer — talks to PostgreSQL. Creates the schema/seed
    data on first run, and exports functions like getDashboard(),
    getMissing(), listDelegates(), account CRUD, etc. server.js just
    calls these. Passwords are stored as bcrypt hashes (hashPassword /
    verifyPassword). Older rows created before hashing was added are
    auto-upgraded in place the next time that account logs in
    successfully (upgradePasswordIfNeeded) — no manual migration needed.
    Also creates Desmond's "TransitFlow" schema (the users + itinerary_items
    tables and the extra trip/coach/delegate columns his Trips board needs) —
    folded into createSchema()/seed() so it auto-applies on startup, instead
    of the standalone SQL migration files his feature originally shipped with.
    delegates."photoUrl"/"photoPublicId" (profile photos, see cloudinary.js
    below) are set ONLY via setDelegatePhoto()/clearDelegatePhoto() — never
    through the generic createDelegate/updateDelegate path — so a client
    can't PATCH in an arbitrary external image URL and skip the upload
    validation.
    delegates."lastLocation" — a free-text place/address, staff-entered via
    the normal create/edit path (normalize()/createDelegate/updateDelegate),
    unlike photoUrl. Not geocoded server-side; the frontend's
    DelegateLocationMap component hands the raw text straight to the Google
    Maps Embed API's `q=` param, which does its own lookup. getMissing() also
    includes it in its output alongside lastSeen. getMissing() also now
    returns each delegate's coachId (needed so DashboardPage.jsx's Reverse
    headcount tab can group missing delegates by coach; it previously only
    returned a pre-formatted "Coach 7 · Suzhou" display string with no id).
    getMissing() also now carries each row's status (always "MISSING" there,
    but DelegateAvatar reads it to tint the avatar red).
    activity_log.actor — the account name that performed each change, so the
    History tracker / History log show WHO did it instead of a generic "you".
    logActivity(text, kind, actor) records it; createDelegate/updateDelegate/
    deleteDelegate/deleteAllDelegates take an optional actor param that
    server.js's delegate routes fill from req.account (actorOf() =
    name || username). rowToActivity() returns it as `via`, falling back to
    "you" for legacy rows / writes with no actor (e.g. teammate modules like
    vimal.js/vance.js that call createDelegate/updateDelegate directly for
    check-ins don't pass one — those show "you"). Nullable column, added via
    ALTER ... ADD COLUMN IF NOT EXISTS, so existing rows aren't attributed
    retroactively (they keep showing "you").
    delegates.createdBy — same actor-snapshot pattern as activity_log.actor,
    but persisted ON the delegate row itself (not just the audit log) so it
    can be its own Dashboard table column ("Created by"). createDelegate()
    already took an `actor` param for the activity-log entry; this just also
    writes it into the new column and returns it on the created row. Wired
    from server.js's POST /api/trips/:id/delegates (single add) and
    vance.js's POST /api/trips/:id/onboarding/confirm (bulk upload) — both
    already had req.account available via their permission gate. NULL/"—"
    for legacy rows or any other creation path that doesn't pass an actor.
    5-status system, step 1 (Dashboard-only basic CRUD) — normalize() (in this
    file) expanded its allowlist from 3 values (PRESENT/MISSING/UNASSIGNED) to
    5 (UNASSIGNED/ASSIGNED/ARRIVED/LATE/MISSING). "PRESENT" is kept as a
    legacy alias mapped to ARRIVED inside normalize() itself — any row or
    write that still says PRESENT (several teammates' QR/face-scan/manual
    check-in routes do — vance.js, vimal.js, exceptions.js — none of them
    touched in this pass) keeps working instead of silently resetting to
    UNASSIGNED. Only DashboardPage.jsx's status <select>s (filter dropdown +
    the add/edit modal) were updated to offer all 5 values; every other
    consumer (TripCoachPage, mobile attendance, QR/check-in screens) still
    only knows the original 3 and is unaffected either way — this is
    deliberately narrow, not a full rollout (see AI Log). StatusBadge.jsx's
    STATE_MAP gained ASSIGNED/LATE entries (new badge-assigned/badge-late CSS
    classes + --st-assigned/--st-late tokens in tokens.css, light+dark) —
    additive only, doesn't change PRESENT/MISSING/UNASSIGNED rendering.
    DashboardPage.jsx also gained a local effectiveStatus(d) helper (aliases
    PRESENT→ARRIVED) used only for the status filter/sort, so legacy rows
    still show up correctly under the "Arrived" filter instead of vanishing.
    Step 2 (done): TripCoachPage.jsx (Desmond's Trip page) — same additive
    pattern. Its own local STATUS_LABEL/STATUS_COLOR2 maps (a THIRD copy of
    the enum, independent of data.js's normalize() and StatusBadge's
    STATE_MAP — see the "5 duplicate enum maps" note in the AI Log) gained
    ASSIGNED ("blue")/LATE ("orange") entries, PRESENT aliased to the
    "Arrived" label/green color same as everywhere else. TripCoachPage.css
    gained matching --tf-orange/--tf-orange-bg/--tf-orange-line tokens
    (light+dark) — this page has its OWN --tf-* color variables, entirely
    separate from tokens.css's --st-* ones, so both had to be extended
    independently. The status filter <select> expanded from 3 to 5 options,
    with the same PRESENT→ARRIVED filter-comparison alias DashboardPage.jsx
    uses. This page still has no direct status editor (unlike Dashboard's
    dropdown) — status only changes via drag-to-coach or the "Move to coach"
    control (handleReassign()). Step 3 (done, follow-up pass): that
    transition originally only knew UNASSIGNED/MISSING (delegate.status ===
    "UNASSIGNED" ? "MISSING" : delegate.status when dropped on a coach) — so
    dropping someone onto a coach immediately marked them MISSING, which
    conflated "just assigned, hasn't had a chance to board yet" with
    "genuinely failed to show up." Changed the UNASSIGNED branch to ASSIGNED
    instead: dropping onto a coach now means "expected here, not yet
    checked in," matching the 5-status model's actual intent — MISSING is
    reserved for a real check-in miss or an explicit staff override, not the
    default outcome of a routine assignment. A delegate who already has a
    real status (ARRIVED/LATE/MISSING/ASSIGNED) still keeps it when moved
    between coaches — only the UNASSIGNED→? branch changed, moving someone
    who already arrived doesn't reset them. Deliberately NOT touched:
    FleetCard's per-coach "X missing" badge, the Hero banner's missingCount
    alert, and DelegateCard's red "is-missing" tint all still check
    `status === "MISSING"` literally, unchanged. This is intentional, not an
    oversight — those counts now more accurately mean "genuinely missing"
    instead of "assigned but not literally PRESENT" (the old 3-status
    reading), which was itself the design flaw being fixed. The visible
    side effect: a delegate freshly assigned via drag no longer inflates any
    "X missing" count anywhere until something actually marks them MISSING
    (today: only a manual override; the Late/10am-cutoff auto-transition is
    still unbuilt — see the deferred items in the 5-status plan). Dashboard's
    and Mobile's own "missing" counts/queries are NOT touched in this pass
    either and will have the same read going forward — a coherent, if
    still-incomplete, picture until the Late/cutoff system exists to
    actually move someone from Assigned into Missing over time.
    resolveTripUuid("t-1") now returns the REAL Beijing trip uuid instead of
    null. WHY (fixed two linked bugs): "t-1" used to mean null = "every
    delegate/coach across ALL trips". Fine while only Beijing had data, but
    once other trips got their own coaches/delegates it meant (a) the base
    Dashboard's Coach status listed OTHER trips' coaches (looked like stray
    placeholders — e.g. 8 coaches shown when Beijing has 7) and (b) a delegate
    added on the base Dashboard was created with trip_id = NULL, so it showed
    on the Dashboard but NEVER on Desmond's Trips board (which filters by trip
    uuid) — e.g. "desmond" was missing from Trips. Scoping "t-1" to Beijing
    makes the base Dashboard and the Trips board the exact same dataset
    (verified: both 34 delegates / 7 coaches, desmond on both). The existing
    seedTransitFlow() startup backfill still attaches legacy NULL-trip rows to
    Beijing so nothing vanishes. Every base-Dashboard read/write (getDashboard,
    getMissing, listDelegates, createDelegate, deleteAllDelegates, export) goes
    through resolveTripUuid, so this single change scopes them all — no
    per-route edits. Note the semantic shift: "Delete all" and "Add delegate"
    on the base Dashboard now act on the Beijing trip specifically, not
    literally every trip's delegates.
    accounts.last_seen_at — stamped by touchLastSeen() every time GET
    /api/auth/session is called (every signed-in client already polls that
    every 15s for the force-logout guard), so this adds no new client
    traffic. listActiveAccounts(withinSeconds=45) returns accounts seen
    within that window — powers the Dashboard's "Staff operations" tab
    "active now" list. clearLastSeen(id) sets it back to NULL — called by
    POST /api/auth/logout so an explicit logout drops off the active list
    immediately instead of waiting up to 45s to age out.

cloudinary.js
    Thin wrapper around the Cloudinary SDK for delegate profile photos.
    uploadImage() forces resource_type:"image", so Cloudinary itself
    decodes/validates the bytes are a real image — not just trusting the
    client's declared Content-Type. Needs CLOUDINARY_CLOUD_NAME/API_KEY/
    API_SECRET in backend/.env (sign up at cloudinary.com — free tier is
    plenty); isConfigured() lets server.js return a clear "not configured"
    503 instead of failing oddly when those aren't set.

routes/desmond.js
    Desmond's "TransitFlow" API — the Trips & Coaches board (list trips,
    per-trip coach/delegate/itinerary CRUD, staff directory, seed demo
    trips, in-memory activity feed). Self-contained: makes its own pg pool.
    "View for all, edit gated": every GET route (and the cosmetic POST
    .../activity) uses requireAuth() (any signed-in account); every other
    write route uses requirePermission("manageTrips") — applied per-route,
    not as one router-level gate, since a blanket gate would also catch
    requests meant for OTHER teammates' routers mounted alongside this one
    (found and fixed while merging in Jayden's exceptions.js). Mounted in
    server.js's TEAMMATE ZONE next to insightsRouter. To avoid colliding
    with the base app's hardcoded single-trip routes it uses new paths like
    /api/all-trips and /api/trips/:tripId/summary.

routes/exceptions.js
    Jayden's Exception Logging & QR Fallback API — ticket CRUD (raise/
    resolve/delete), manual attendance override, and a live Server-Sent
    Events channel (GET /api/exceptions/stream) that pushes ticket changes
    to every connected staff device in real time. Self-contained: makes its
    own pg pool and creates its own tables (exception_tickets, shared
    check_in_logs) via initExceptions(), called once from server.js's
    startup chain after initDb(). "View for all, edit gated": reads (+ the
    SSE stream) use requireAuth(); raising/resolving/deleting a ticket or a
    manual override use requirePermission("manageExceptions"). Its original
    auth code decoded the old pre-JWT token format by hand — rewritten at
    merge time to use auth.js's requireAuth/requirePermission like every
    other route. Also has POST /api/checkins/qr (Jayden's QR half of the
    /checkin screen — writes a method='QR' row to the shared check_in_logs
    table and flips the delegate PRESENT) — gated on requireAuth() only,
    same level as Vimal's face scan, not the elevated manageExceptions used
    by manual overrides. Idempotent on client_event_id.
    exception_type has a 6th value, "OTHER", carrying a free-text label in
    the new exception_tickets.type_other column (VARCHAR(TYPE_OTHER_MAX=20),
    added via ALTER TABLE ... IF NOT EXISTS so an already-deployed DB picks
    it up on next boot). exception_priority already had "LOW" in its enum
    from the start, but nothing in the UI ever exposed it until this same
    change — Critical/Normal/Low is now a real 3-tier system end to end.
    POST /api/trips/:id/exceptions validates type against the enum itself
    (400 instead of an opaque Postgres 500 on a bad value), requires
    typeOther (trimmed, capped) when type is "OTHER", and validates priority
    the same way. Cherry-picked from Jayden's upstream branch
    (`origin/SecureScan-Logs-(Jayden)`) — see the "INTEGRATING TEAMMATE
    BRANCHES" note near the bottom of this file for why this was a
    selective port, not a file merge.

routes/vimal.js
    Vimal's FaceCheck-Pro — Privacy-First Biometric & Multi-Modal Fusion
    Scanner. Powers the /checkin screen's "Trips" (reverse-headcount muster
    view), "Scan → Face" tab, and "Me" (consent + history) tab. Self-
    contained: imports JQ's own listDelegates/getDelegateById/updateDelegate/
    createDelegate/getTrip/getDashboard from data.js (never edits it), so a
    face check-in writes through to the REAL shared delegates table and
    every other screen (dashboard, mobile, Trips board) sees it instantly.
    Coach lookups go through getDashboard(), so coaches added later by
    Desmond's module work here automatically. PDPA-by-design: the server
    NEVER receives or stores an image/audio clip — the browser vectorizes
    one off-DOM camera frame into an irreversible token ("face:v1:<hex>:…"),
    zeroes the raw pixel buffer in place, and only the token is ever sent.
    Consent lifecycle + per-delegate check-in history are kept in-memory
    (Maps, not the DB) — Vimal-owned bookkeeping, separate from the shared
    delegate records. Endpoints: GET /api/attendance/coaches, POST /api/
    attendance/scan, GET /api/attendance/:trip_id/coach/:coach_id, GET /api/
    attendance/headcount, POST /api/attendance/consent, GET /api/attendance/
    history/:delegate_id, POST /api/attendance/assign-unassigned (muster
    UNASSIGNED delegates onto a coach), POST /api/attendance/demo-seed. All
    gated on requireAuth() only — any signed-in staff can scan, matching the
    QR check-in's auth level rather than the elevated manageExceptions tier.
    Shares the /checkin screen with Jayden's QR/Manual/Issues panels (see
    QRCheckInPage.jsx below) — the two features were built independently
    against reserved slots in the same shell and verified not to collide
    (own camera streams, no shared re-fetching, namespaced CSS/routes).

routes/vance.js
    Vance's DocuSync AI + Trip Assistant API — three features. (1) Document
    parsing: an uploaded directory / attendee list / spreadsheet / scanned
    passport is read (text via the `unpdf` package, or Claude vision for
    scans/images) and turned into structured delegate rows with a confidence
    score; on confirm they're written to the SHARED delegates table via
    data.js's createDelegate(), and each gets a unique `qr_code` (e.g.
    "MG-86B620A4") minted by newQrCode(). (2) QR boarding passes + on-site
    check-in: GET /api/onboarding/badges returns every delegate + their QR
    token for a trip (auto-backfills a qr_code for any delegate that predates
    this feature, via backfillQrCodes()); POST /api/onboarding/checkin
    resolves a scanned/tapped code, flips the delegate PRESENT (+ coach), and
    logs a QR row to the SHARED check_in_logs table — the same table Jayden's
    manual override and Vimal's face scan write to, and the one Desmond's
    coach board reads, so a boarding-pass scan shows up everywhere instantly.
    The logged trip is derived from the DELEGATE's own trip (JOIN through
    trips.uuid_id), not the client-supplied tripId — so a mistyped/mismatched
    tripId in the request can't file a check-in against the wrong trip; it
    only falls back to the request's tripId for base-pool delegates with no
    trip set.
    Both gated on requireAuth() only (any signed-in staff), matching Vimal's
    face-scan auth level rather than the elevated manageExceptions tier.
    (3) Trip assistant chatbot: answers questions over a live snapshot of
    everyone's data (delegates/coaches/exceptions/check-ins/itinerary),
    streaming replies token-by-token, with saved chat history. The prompt is
    strict about not mixing up present/missing/unassigned and about not
    volunteering unrequested detail (answer only what was asked, then stop).
    Self-contained: own pg pool, own tables created lazily on first use via
    ensureReady() (extra delegate columns incl. qr_code + a partial unique
    index + chat_sessions/chat_messages). Parsing and confirming require
    manageDelegates; the chatbot and the boarding-pass/scan endpoints are any
    signed-in user. Parsing prefers Claude (needs ANTHROPIC_API_KEY; required
    for scans); the chatbot is Ollama-first then Claude, like insights.js.
    GET /api/onboarding/context, POST /api/trips/:id/onboarding/confirm, and
    GET /api/onboarding/badges now resolve their tripId via data.js's shared
    resolveTripUuid() instead of an ad-hoc `SELECT uuid_id FROM trips WHERE
    id = $1`. WHY: trips.id is a legacy short code that's ONLY ever "t-1" for
    the seed trip — every other trip's `id` column holds an unrelated random
    uuid (see desmond.js's `gen_random_uuid()::text` in its trip-seed
    INSERT) — so the old lookup silently matched nothing for any trip except
    the base one, and every write/read fell back to unscoped (trip_id NULL)
    behavior. This was the real cause behind "pre-event uploads don't reach
    the arrival check-in module" for any non-Beijing trip. onboarding/confirm
    also now passes the resolved tripUuid directly into createDelegate()'s
    2nd param (not just a follow-up UPDATE), so a delegate is correctly
    scoped from its very first INSERT. POST /api/onboarding/checkin's own
    trip-derivation (LEFT JOIN through the delegate's own trip_id, see the
    comment there) was already correct and untouched.

backend/seed-demo.js
    One-off script (npm run seed:demo) that seeds a realistic delegate
    roster (via data.js's own createDelegate, so rows are shaped exactly
    like the rest of the app expects) plus 7 sample exception tickets, so
    the Exceptions inbox and Trips board aren't empty on a fresh database.
    Safe to re-run — skips seeding whatever already exists.

backend/seed-team.js
    One-command setup (npm run seed:team) that creates ONE login account per
    team member (jq / vance / desmond / jayden / vimal, each "password123!",
    full access), so nobody has to share staff_194. WHY IT MATTERS: logins
    enforce a single active session (auth.js bumps token_version each login),
    so when the whole team shares staff_194 they constantly log each other
    out ("Your account is no longer valid" every ~15s). Using your OWN account
    fixes it. Safe to re-run — never overwrites an account that already exists.

backend/reset-login.js
    One-command fix (npm run reset:login) for "I cloned the repo and can't
    log in." The team shares ONE Neon database and `git clone` only resets
    CODE, not the DB — the seeded staff_194/password123! login only applies
    on a first boot against an empty DB, so once the shared DB drifts (a
    changed password, a teammate's old branch writing to accounts) the
    documented credentials stop working. This force-resets staff_194 back to
    password123! with full main permissions (creating it if missing). Safe
    to re-run; override target with RESET_USER / RESET_PASS env vars.

routes/insights.js
    Powers the "Generate Insights" button on the Dashboard's Analytics tab.
    Requires a signed-in account (requireAuth, from auth.js). Tries a
    local Ollama server first (free, no key, nothing leaves your
    machine); if Ollama isn't running, falls back to the Anthropic API
    (needs ANTHROPIC_API_KEY in .env). If neither is available, returns a
    clear "not configured" message instead of erroring. Also honors the
    current UI language — asks the model to write directly in English or
    Chinese, so no separate translation step is needed. buildPrompt() now
    forces a fixed 3-point structure — "1. Overall: ... / 2. Missing: ... /
    3. Advice: ..." (translated labels in SECTION_LABELS for zh) — instead
    of freeform 3-5 points, so staff always get the same read: attendance
    health, who's missing, then concrete next actions/who to contact. Found
    via live testing (local Ollama): the instruction telling the model the
    label-prefix pattern used a literal meta-placeholder — `"N. ${"{Label}"}:
    "` — which a weak local model echoed VERBATIM into every point ("N.
    Overall: ...") instead of substituting a real digit. Fixed by spelling
    out the substitution rule in plain English with a concrete worked example
    ("the first point must literally begin '1. Overall: '") and an explicit
    "never write the letter N" instruction.

package.json / package-lock.json
    Dependencies (express, pg, exceljs, cors, dotenv, @anthropic-ai/sdk,
    bcryptjs, jsonwebtoken, unpdf) and the scripts: "npm run dev",
    "npm start", "npm run seed:demo", "npm run reset:login",
    "npm run seed:team".

    OLLAMA_HOST / OLLAMA_MODEL / ANTHROPIC_API_KEY / ANTHROPIC_MODEL for

FRONTEND/  (React + Vite SPA, port 5173)
------------------------------------------

Entry point & routing:

  main.jsx
      The actual entry point — mounts React to the DOM, wraps everything
      in BrowserRouter and LanguageProvider (the translation context),
      imports the global tokens.css.

  App.jsx
      The router. Decides auth state, and maps every URL path
      (/dashboard, /assistant, /mobile, etc.) to its page component.
      This is the file to check first when you want to know "what page
      does this URL show." Also remembers whether you were in the mobile
      section before logging out, so signing back in returns you there.

  vite.config.js
      Dev server config — proxies /api/* calls to the backend on :4000
      so the frontend never needs to think about CORS.
      server.strictPort: true — without this, Vite silently falls back to
      the next free port (5174, 5175...) whenever 5173 is already held by a
      leftover process (this project's dev servers are prone to that — see
      the note on preview_stop leftovers elsewhere in this doc). That's not
      just cosmetic: Chrome's password manager and any browser-stored
      session scope credentials/state per-origin INCLUDING the port, so a
      "remember password" save made while running on :5173 silently stops
      autofilling the moment a later run drifts to :5174 — no error, it just
      looks like the remember-password feature is broken. strictPort makes a
      stale process on 5173 fail loudly instead, so it gets killed rather
      than routed around.

Shared components (src/components/):

  Layout.jsx
      The desktop shell — renders Sidebar + whatever page is routed into
      the main content area. Also polls the backend every 15s to catch
      if your account got edited/deleted while logged in, and separately
      polls lib/exceptionsApi.js's getCriticalOpenCount() every 15s to
      drive the Sidebar's live "Exceptions" badge (used to be hardcoded
      demo state).
      • Collapsible sidebar (<=1024px, i.e. tablet and narrower): owns the
        sidebarOpen state, renders the .app-topbar-collapsed hamburger bar
        and the .app-sidebar-backdrop (click-to-close), and auto-closes the
        drawer on every route change. Above 1024px none of this renders
        visibly — the sidebar stays exactly as it always was (sticky,
        always open, no hamburger). See tokens.css's collapsible-sidebar
        block for the actual open/closed CSS.
      Renders <ChatBubble /> once alongside <Outlet/>, so the floating chat
      widget persists across every desktop route (see ChatBubble.jsx below).

  Sidebar.jsx
      The left nav rail — links to every page, the EN/中文 toggle, and
      the account/logout block at the bottom. The account block (avatar +
      name/role) links to /settings and has a hover highlight
      (.sidebar-account); the sun/moon dark-mode toggle sits right beside it.
      Takes an `open` prop from Layout.jsx (applies the .sidebar.open class);
      unused/ignored above the 1024px breakpoint. "Check-in" nav item links
      to /checkin (QRCheckInPage.jsx) — ungated, any signed-in staff.
      "Chat assistant" nav item removed — the AI Trip Assistant is now a
      floating bubble (ChatBubble.jsx), not a dedicated destination.

  ChatBubble.jsx
      New. Floating chat widget, rendered once from Layout.jsx so it's
      available on every desktop route (replaces the old dedicated

Library helpers (src/lib/):

  api.js
      The HTTP client — apiGet/apiPost/apiPatch/apiDelete, all
      auto-attaching your JWT. Also handles token/user storage (login
      persistence).

  i18n.jsx
      The translation system — the English/Chinese dictionary,
      useLang() hook (returns { lang, toggleLang, t }), and language
      toggle logic. Also exports translate() for code outside React
      rendering (e.g. window.alert/confirm messages). Static dictionary
      only — no data ever sent to a translation API, so delegate
      names/live data are never exposed.

  theme.jsx
      App-wide light/dark theme — ThemeProvider + useTheme() hook (returns
      { theme, toggleTheme }), persisted to localStorage (mg_theme), stamps
      data-theme="dark" on <html>. tokens.css's :root[data-theme="dark"]
      block overrides the neutral/surface/status-tint variables everything
      (.card/.btn/.input/the sidebar/etc.) is built on, so one toggle
      re-themes every page. TripsListPage's useTfTheme() is now just a thin
      wrapper around this (no more separate tf_theme localStorage key), so
      the Trips/Coach board pages follow the same toggle too.

  claudeParse.js
      Vance's parse/confirm bridge for the Onboarding page — uploads a file
      to backend/routes/vance.js (POST /api/documents/parse), polls the
      async parse job, and commits the reviewed rows (onboarding/confirm).
      Real backend now, not a demo.

  exceptionsApi.js
      Jayden's data layer for the Exception Inbox — built on the shared
      apiGet/apiPost/apiPatch/apiDelete (inherits token storage/typed
      errors for free) plus subscribeStream() for the live SSE channel
      (EventSource, token passed as ?token= since it can't set headers)
      and getCriticalOpenCount() (used by Layout.jsx's sidebar badge).
      checkInByQR() (POST /api/checkins/qr) was added for the /checkin
      screen's QR pill, but QRScannerPanel.jsx no longer calls it — see the
      QRScannerPanel.jsx entry below for why (unused, left in place).
      TYPE_OTHER_MAX/PRIORITIES/BASE_PRIORITIES/issueLabel() added — mirrors
      backend/routes/exceptions.js's "Others" type + 3-tier Critical/Normal/
      Low priority. issueLabel(ticket) returns the ticket's custom typeOther
      label when set, else the ISSUE_LABEL[type] fallback (kept exported,
      still used as issueLabel()'s own fallback). createException() gained
      typeOther/priority params; markCritical is still honoured for backward
      compatibility (always forces CRITICAL when passed).

  useSessionGuard.js
      Shared hook (Layout.jsx + MobileLayout.jsx): polls GET /api/auth/
      session every 15s + on window focus, force-logs-out on a 401 (token
      invalidated — renamed/deleted account, or a newer login elsewhere
      bumped token_version) or a permissions/username change. Extracted
      from Layout.jsx so mobile gets the same behavior — see the note on
      MobileLayout.jsx above for why that mattered.

Styles (src/styles/):

  tokens.css
      The whole design system — colors, buttons, cards, badges, tables,
      the sidebar/page layout. Loaded globally. .select now gets a custom
      chevron-down icon (appearance:none + an inline SVG background-image)
      instead of each browser's own native arrow — any inline style on a
      <select className="select"> that overrides padding must leave room on
      the right (padding-right >= ~28px) or the icon will overlap the text;
      see OnboardingPage.jsx's coach-picker and MobileAttendancePage.jsx's
      status <select> for the pattern.
      `html { zoom: calc(var(--app-zoom) * 100%); }` (--app-zoom: 0.99 —
      originally 1.1, lowered per user preference; see below — defined in
      :root) bakes in a fixed visual scale so the app reads at a
      consistent, comfortable size at every viewer's own 100% browser zoom —
      same look across Chrome/Edge/Safari/Firefox 126+, since it's part of
      the page instead of a per-browser manual zoom setting. Uses `zoom` (not
      `transform: scale`) so it participates in normal layout — scrollbars,
      viewport units, and click hit-testing all stay correct in MOST cases
      (see the --sidebar-w / .sidebar note below for the one real exception
      this surfaced).
      Dark theme (:root[data-theme="dark"]) was softened — was near-black
      (--bg #121417, --surface #1a1d22); now a lighter charcoal (--bg
      #1a1d21, --surface #24272c, --surface-2 #2a2e33), same relative
      structure (bg < surface < surface-2), just lifted several steps.
      .sidebar's `height: 100vh` — a REAL bug, not just cosmetic, was found
      here: `zoom` scales the RENDERED box of everything, but `vh` units and
      the browser's own overflow detection (scrollHeight/clientHeight) are
      computed in PRE-zoom layout space. So on a viewport-CLAMPED sticky
      element like the sidebar, `height: 100vh` rendered as 100vh × 1.1 of
      ACTUAL visual space — the bottom ~10% (the Log out button) silently
      overflowed the real screen, and because the browser's own layout math
      didn't consider it "overflowing" (both measured pre-zoom, so they were
      equal), `overflow-y: auto` didn't even trigger a scrollbar to reach it.
      A real user got completely locked out of the Log out button. Two
      wrong attempts before the real fix: (1) `overflow-y: hidden` traded
      the "unwanted scrollbar" complaint for silently clipping the footer
      with zero way to reach it — worse, not better; (2) just restoring
      `overflow-y: auto` alone didn't help either, since (per the paragraph
      above) the browser doesn't detect this as overflow in the first place.
      The actual fix: `.sidebar`'s height is `calc(100vh / var(--app-zoom))`
      — dividing cancels the zoom's scale-up so the RENDERED box is exactly
      one real viewport tall, matching what `100vh` is supposed to mean.
      `overflow-y: auto` is kept as a defensive safety net on top (content
      that still somehow doesn't fit — an unusual OS font size, a longer nav
      list later — stays reachable by scrolling instead of disappearing).
      Sidebar padding/gaps were also trimmed a little (20px→16px container
      padding, 4px→2px item gap, 10px→8px per-item vertical padding) so
      scrolling is rarely actually needed on a normal screen. Any OTHER
      element that uses `100vh`/`100vw` for a viewport-CLAMPED (not
      page-scrollable) size must divide by `--app-zoom` the same way — plain
      page content using `min-height: 100vh` (like `.app-shell`) is fine
      as-is, since overshooting there just makes an already-scrollable page
      a little taller, which is harmless.
      --app-zoom later changed from 1.1 to 0.99: user compared the app in
      Chrome at their browser's default 100% zoom (effective size = 1.0 ×
      1.1 = 110%) against manually zooming Chrome to 90% (effective size =
      0.9 × 1.1 = 99%) and preferred the smaller one. Rather than ask every
      viewer to manually zoom their browser, baked that same ~99% net size
      in as --app-zoom directly, so it's the default at anyone's normal
      100% browser zoom. The `calc(100vh / var(--app-zoom))` sidebar-height
      fix above is a general formula that holds at any zoom value above OR
      below 100% — no additional change needed there when this was lowered.

  mobile.css
      Mobile-only classes (.mobile-shell, .mobile-card, .mobile-tabbar,
      etc.), scoped so it can't clash with the desktop styles.


HOW TO TRACE A PAGE
--------------------
1. Start at App.jsx to find which page a URL loads.
2. Open that page file.
3. If it needs live data, it calls apiGet/apiPost from lib/api.js.
4. That hits a route in backend/server.js (or backend/routes/*.js).
5. Which calls a function in backend/data.js (or, for AI Insights,
   talks to local Ollama / the Anthropic API).


AUTH & SECURITY
-----------------
- Session tokens are signed JWTs (backend/auth.js), not forgeable.
  Set JWT_SECRET in backend/.env before deploying anywhere public.
- Passwords are bcrypt-hashed (backend/data.js). Legacy plaintext rows
  auto-upgrade on next successful login — nobody needs to run a migration.
- Every API route requires a signed-in account at minimum; mutating
  actions (delegate CRUD, accounts, export) additionally require the
  matching permission from permissions.js, enforced server-side (not
  just hidden in the UI).
- Because tokens changed format, everyone gets signed out once after
  this update and needs to log back in — expected, one-time.

- RBAC — EXACTLY TWO ROLES (Admin / Staff). The old "main" tier (derived
  whenever manageAccounts was ticked) is retired; role is now an independent,
  explicitly-set field (the Account control role picker), not derived from
  permission checkboxes.
    · Admin BYPASSES every permission check. accountPermissions(row) in
      data.js returns every key as `true` for role="admin" regardless of
      what's actually stored — so requirePermission() (auth.js) and every
      getPermissions().xyz check on the frontend automatically unlock for
      admins, with zero per-call special-casing. Admin sees every Dashboard
      tab (Delegate/Analytics/Staff operations), every Sidebar item, and
      Account control.
    · Staff are governed by the stored checkboxes (permissions.js's 5 keys),
      defaulting to just "Manage delegates" — i.e. the Dashboard's Delegate
      tab, the typical staff-facing surface. DashboardPage.jsx additionally
      hard-gates the Analytics tab on role==="admin" (not a checkbox) — a
      Staff account never sees it, however the permissions are configured.
    · "Last admin" protection: updateAccount()/deleteAccount() in data.js
      block demoting or deleting the only account with role="admin" (would
      lock everyone out of Account control) — countAdmins() replaces the old
      countManagers()/manageAccounts-flag check. Error code stays "LAST_MAIN"
      for frontend compatibility; the displayed message now says "Admin".
    · Migration: seed()'s startup routine runs
      `UPDATE accounts SET role = 'admin' WHERE role = 'main'` every boot
      (idempotent — a no-op once none are left), so the team's shared Neon
      DB picks this up automatically on next deploy/restart, no manual DB
      edit needed. backend/seed-team.js and backend/reset-login.js were also
      updated to seed role='admin' instead of 'main'.
    · AccountControlPage.jsx's role picker always shows a Staff/Admin toggle
      (no more "this is the protected Main account, checkboxes only"
      special case) — picking Admin hides the permission checkboxes
      entirely (they're moot; admin bypasses regardless) and shows a note
      instead; picking Staff shows the real, enforced checkboxes.
- "Remember password" (login page) is now SECURE / TOKEN-BASED — it no
  longer stores the password anywhere. Ticking it only controls whether the
  signed JWT persists in localStorage (survives closing the browser) vs
  sessionStorage (cleared when the tab/browser closes), via the existing
  setToken(token, keep) call. LoginPage.jsx purges any plaintext password an
  earlier build already wrote under the old "mg_remember"/"mg_remember_v2"
  keys on load, for every returning visitor. This reverses the earlier
  restored plaintext-password-remembering behavior (see AI Log) at explicit
  user request, for a different, security-focused reason this time.


TESTING THE MOBILE UI ON A PHONE
-----------------------------------
Both dev servers already support this (vite.config.js has host: true,
Express listens on all interfaces by default) — no code changes needed:

  1. Connect your phone to the same Wi-Fi as this computer.
  2. Run `npm run dev` in both backend/ and frontend/ as usual.
  3. Find this computer's local IP (Windows: ipconfig -> IPv4 Address,
     e.g. 192.168.1.11).
  4. On the phone's browser, go to http://<that-IP>:5173/login, sign in,
     and it'll land you on /mobile automatically.
  5. If it won't load, Windows Firewall is the usual culprit — allow
     Node.js through the firewall for Private networks (or allow ports
     5173/4000). The phone only needs port 5173 — Vite's dev proxy
     forwards /api/* to the backend on this machine's side.

CAN'T LOG IN AFTER CLONING? (shared-database gotcha)
--------------------------------------------------------
The team shares ONE Neon database. `git clone` resets your CODE but NOT the
database — so the seeded `staff_194 / password123!` login (which only runs
on a first boot against an empty DB) may not match what's currently stored
in the shared DB. If someone changed the password, or a teammate on an older
pre-bcrypt branch wrote to the accounts table, the documented credentials
stop working for everyone.

Fix it in one command (no more editing Neon by hand):

  cd backend
  npm run reset:login        # staff_194 back to password123!, full access

Note: because logins now enforce a single active session, when YOU reset and
log in, other people's staff_194 sessions get logged out. Longer term, each
developer having their own Neon database (free tier allows several) avoids
this class of problem entirely.


GETTING LOGGED OUT EVERY ~15 SECONDS? ("Your account is no longer valid")
------------------------------------------------------------------------
Logins enforce a SINGLE ACTIVE SESSION per account (auth.js bumps a
token_version on every login; the 15s session poll logs out any session whose
token is behind). That is correct for one person — but if the WHOLE TEAM
shares `staff_194` on the shared database, every login anywhere (a teammate,
another clone, another tab) invalidates everyone else, so you get kicked out
constantly even while idle.

Fix: give each person their OWN account, then sign in as yourself, not
staff_194:

  cd backend
  npm run seed:team          # creates jq / vance / desmond / jayden / vimal
                             # (each "password123!", full access)

Your session then only ends when YOU log in elsewhere — not when a teammate
does.


EXCEPTIONS FEATURE — SEEDING DEMO DATA
------------------------------------------
The Exception inbox and Trips board start empty on a fresh database (the
base app only seeds a trip, 4 coaches, and the first login). To populate
them with a realistic delegate roster + 7 sample tickets:

  cd backend
  npm run seed:demo

Safe to re-run — it skips seeding whatever already exists. By default,

account raise/resolve/delete tickets or do a manual override; everyone
signed in can already view the inbox and live alerts.


INTEGRATING TEAMMATE BRANCHES (e.g. from C:\fsad\Project\integration\...)
---------------------------------------------------------------------------
Teammates' work sometimes arrives as a full clone/checkout of their branch in
a sibling `integration/` folder rather than a PR against this repo. Two
lessons learned merging Jayden's `SecureScan-Logs-(Jayden)` branch a second
time (2026-07-17, after an earlier successful merge on 2026-07-15):

1. CONFIRM IT'S REALLY NEWER before touching anything. `git fetch origin`
   inside the integration clone + compare against its tracked remote branch —
   don't assume a folder labeled "integration" is automatically ahead of what
   was already merged. This time it genuinely was (a real new commit,
   "QR scanner: accept Vance's boarding-pass codes" — coincidentally the same
   headline as a fix already made independently in this project days earlier,
   which is what makes checking essential rather than assuming).

2. DIFF EVERY FILE, but expect MOST diffs to be false positives. A teammate's
   branch is usually an old snapshot relative to this project's own fast-
   moving trunk — diffing shared/foundational files (data.js, server.js,
   App.jsx, Sidebar.jsx, tokens.css, i18n.jsx, lib/api.js, any page not owned
   by that teammate) will show "differs" almost everywhere, but that's THIS
   PROJECT having moved on, not the teammate having added something. Blindly
   overwriting any of those would silently REVERT real, already-shipped work
   (this pass alone would have reverted the RBAC/dark-theme/zoom/rate-
   limiting/mobile-refactor changes from the same day). Only cherry-pick the
   files the branch's OWNER actually touched for their OWN feature, and even
   then verify feature-by-feature, not file-by-file:
     - A file can carry BOTH a genuine new feature AND stale drift in the
       same diff (Jayden's exceptions.js/IssuesPanel.jsx/LogExceptionModal.jsx
       had a real, valuable "Others" issue-type + Low-priority feature mixed
       in with hardcoded `#fff` backgrounds that would have broken dark mode,
       and — in the two exception-inbox files specifically — every
       `useLang()`/`t()` call stripped entirely, which would have silently
       killed Chinese translation on that page). The fix was to hand-port
       just the new logic into the CURRENT versions of those files (Edit, not
       Read+Write-over), not take the diff wholesale.
     - A file can look like a genuine new feature but be a REGRESSION of a
       deliberate earlier fix (QRScannerPanel.jsx reintroduced the JSON
       DELEGATE_BADGE format + Jayden's own POST /api/checkins/qr endpoint
       that an earlier merge had specifically retired — see the
       QRScannerPanel.jsx entry above). Trace whether the "new" thing is
       actually reachable in the live app (grep the WHOLE branch for what
       generates/prints it, not just what accepts it) before assuming it's
       worth merging.
   When something like this shows up, STOP and ask before finalizing — don't
   silently pick a side. This time: presented both findings (the real feature
   + the two conflicts) to the user with concrete evidence, and asked how to
   proceed; the offered options were "cherry-pick the safe feature only"
   (chosen), "also take the reverted QR format," or "show me the raw diffs
   first."
